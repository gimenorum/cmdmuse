# 設計

cmdmuse が**なぜこの作りなのか**を書く。開発の進め方は [CONTRIBUTING.md](../CONTRIBUTING.md) を参照。

## 全体の流れ

1. `main.go` の REPL ループが `internal/editor` に1行ぶんの入力を読ませる
2. 行の中に `AI(...)` があり、手が5秒止まったら `internal/llm` がモデルに問い合わせる
3. モデルは**候補**を3〜5件返す。1件ぶんは「実行するコマンド」と
   「そのコマンドが使えるための前提」の組になっている
4. `internal/probe` が前提を確かめ、候補ごとに `✓` / `⚠` を付ける
5. 利用者が1件選んで `Enter` を押すと、`main.go` がその行を `$SHELL` に渡す

代替スクリーンに入らないので、実行結果はそのまま端末に流れる。

## 用語

**候補** — `AI(...)` 1回の問い合わせに対してモデルが返すコマンドの案。画面に3〜5件並ぶ。

**probe** — 候補が使えるかを確かめるための短いコマンド。モデルが候補と一緒に書く。
「ここは git のリポジトリか」なら `git rev-parse --git-dir`、
「`rename` が入っているか」なら `command -v rename`。**cmdmuse がこれを実行する。**

**補完** — `AI(...)` を使わない普通の入力に対して出す、コマンド名やパスの続き。
モデルは関わらない。

## パッケージ構成

```
internal/complete 補完 (PATH 走査と ReadDir。シェルを介さない)
internal/expand   AI(...) の切り出し (引用符・入れ子括弧を解釈)
internal/editor   行エディタ。bubbletea を代替スクリーン無しで使う
internal/llm      候補生成 / 解説 / 深堀りの3プロンプト
internal/spec     --help と man を統合してフラグ実定義を取得
internal/probe    probe の実行 + 副作用の静的判定
internal/session  tmux / PSReadLine / 履歴から文脈を取得
internal/core     パッケージ間で共有する型
```

## probe の実行範囲を絞る

probe はモデルが書いた文字列で、それを cmdmuse が実行する。ここが一番危ないので、
実行する側で範囲を決めている。

- **シェルを一切介さない** — `exec` に argv を直接渡すので、`;` や `` ` `` は展開されない
- **コマンド名の許可リスト** — 状態を読むだけのものしか入れない
- **サブコマンドも個別に許可** — `git config --get` は通すが `git config --global x y` は通さない
- **破壊的フラグを個別に排除** — `find -delete` / `-exec` など

一覧に無いものをモデルが書いてきたら実行せず、その前提は「確認できませんでした」になる。
`rm -rf /` や `` `rm -rf /` `` を含む26パターンが実行に到達しないことを
`internal/probe/probe_test.go` の `TestRejectsDangerous` で固定してある。

probe とは別に、**候補のコマンド自体は決して自動実行されない**。
`Enter` で確定したときだけ `$SHELL` に渡る。

## 補完もシェルを使わない

bash の `compgen` に委譲すると、編集中の行が `bash -c` を通る。
`echo $(date)` まで打った状態で Tab を押すと `date` が実際に走る、という類のことが起きる。
`PATH` の走査と `os.ReadDir` で同じ結果を作れるので、そちらで完結させている。

## フラグの意味を生成させない

`--help` と `man` の両方を読んで統合する。片方だけでは足りないことが多く、たとえば GNU find の
`--help` は要約しか出さず `-name` は man にしかない。束ねた短フラグ (`-lah`) は分解して個別に引く。

取れた定義だけを context に入れ、モデルには「この定義だけを根拠に要約せよ」と指示する。
定義が取れなかったフラグは「取得できませんでした」と書かせる。
ここを緩めると、それらしいが間違った解説が出るようになる。

## 候補には違うコマンドを並べさせる

`AI(...)` 1回で出す3〜5件のことを言っている。放っておくと全件が同じコマンドのフラグ違いになる。
プロンプトで「系統の違うコマンドから選べ」と例示すると `tr` / `paste` / `awk` / `xargs` の
ように散る。

候補どうしが同じかどうかは「コマンド名 + サブコマンド + 最初のフラグ」で判定する。
最初のフラグまで含めないと `git merge --no-ff` と `git merge --squash` が同じものとみなされ、
片方が候補から消える。

## モデルに行全体を書かせない

`AI(...)` の前後を `LineContext` として渡し、「断片だけを書く」「前段がパイプなら
標準入力を受ける」と明示する。これが無いと `ls | AI(...)` に対して `ls | tr ...` のように
`ls` を二重に書いてくる。

## 印字可能文字は行の編集に使う

深堀りの起動は `?` ではなく **Ctrl+O**。`?` に割り当てると、正規表現やグロブに `?` を含む行が
打てなくなる。同じ理由で、行の編集に使える文字を操作キーに取らない。

## Ctrl+C は段階的

生成中なら生成だけ中止し、候補表示中なら候補だけ畳み、それ以外で行を破棄する。
5秒待って出てきた候補を1回の `Ctrl+C` で全部捨てて打ち直しにさせない。
